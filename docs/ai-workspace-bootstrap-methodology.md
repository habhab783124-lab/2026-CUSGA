# 新项目 AI 工作环境搭建方法论

Updated: 2026-04-21

## 这份文档的定位
这不是“当前塔防项目介绍”，而是一份可复用的方法论文档。

它同时也是一份需要持续维护的长期文档。

以后只要以下任一内容发生变化，就要同步更新这份文档：

- AI 工作环境搭建方式
- 记忆文档体系
- 智能体准则
- 文档更新机制
- skill 的设计边界与组织方法

它的目标是告诉其他智能体：

- 进入一个新的 Unity 项目后
- 应该先建立哪些基础文件和工作约定
- 如何快速搭出和本项目同等级的 AI 协作工作环境

这里的方法，来自当前项目已经被验证过的一整套做法：

- `AGENTS.md`
- `docs/ai-memory/` 记忆体系
- 玩法规范文档
- 文件结构说明
- 人工验证清单
- 文档更新机制
- skill 设计边界

## 一、先建立基础环境，而不是先写代码
如果一个项目希望长期让多个智能体协作，第一步不是马上写玩法代码，而是先搭基础环境。

原因很简单：

- 没有统一入口文档，智能体每次都要重新猜项目规则
- 没有记忆体系，长线项目会不断重复沟通同样的问题
- 没有验证清单，后期问题会越来越难追
- 没有文件结构规范，脚本和文档会很快失控

所以推荐顺序永远是：

1. 先搭文档骨架
2. 再写智能体准则
3. 再约定 skill 和工作流边界
4. 最后才开始正式做功能

## 二、建议的基础目录结构
新项目建议至少先建出这套目录：

```text
AGENTS.md
docs/
  ai-memory/
    memory-index.paths.txt
    <project>-memory-main.md
    <project>-memory-architecture.md
    <project>-memory-rules-and-history.md
    <project>-agent-development-playbook.md
    <project>-project-file-guide.md
    tools/
  gameplay-spec.md
  manual-validation-checklist.md
  project-structure-overview.md
  art-replacement-workflow.md
Assets/
  Scripts/
  Scenes/
  Prefabs/
```

如果项目是 Unity 项目，再往下建议直接预留脚本分类目录：

```text
Assets/Scripts/<ProjectName>/
  Core/
  Map/
  Placement/
  Towers/
  Enemies/
  UI/
Assets/Editor/<ProjectName>/
  Authoring/
  Validation/
```

这些目录是“通用模板”。

真正需要按项目内容定制的是：

- `<project>-memory-main.md` 等文件名
- `gameplay-spec.md` 的实际玩法内容
- `Assets/Scripts/<ProjectName>/` 下的分类命名

## 三、必备文档清单
一个可长期协作的项目，至少应有以下文档。

### 1. `AGENTS.md`
作用：

- 作为整个项目的总入口
- 告诉智能体先读什么、后读什么
- 约束执行方式和文档更新方式

最少应包含：

- Workspace 身份
- Startup Protocol
- Project-Specific Rules
- Memory Update Triggers

### 2. 主记忆文档
示例命名：

- `docs/ai-memory/<project>-memory-main.md`

作用：

- 作为项目长期记忆总览
- 汇总导航、当前状态、长期约束、阶段进度、关键事实

### 3. 架构文档
示例命名：

- `docs/ai-memory/<project>-memory-architecture.md`

作用：

- 解释模块边界
- 说明哪些职责在总控层，哪些应下沉到子组件
- 记录长期架构原则

### 4. 规则与历史文档
示例命名：

- `docs/ai-memory/<project>-memory-rules-and-history.md`

作用：

- 记录当前已知问题
- 记录最近进展
- 记录长期规则
- 记录已确认过的历史决策

### 5. 开发手册 / playbook
示例命名：

- `docs/ai-memory/<project>-agent-development-playbook.md`

作用：

- 告诉后续智能体“每次开工前怎么进入项目”
- 告诉后续智能体“当前优先顺序是什么”
- 告诉后续智能体“有哪些长期约束必须一直遵守”

### 6. 文件指南
示例命名：

- `docs/ai-memory/<project>-project-file-guide.md`

作用：

- 让智能体快速知道：
  - 哪个文件是入口
  - 改什么先看哪里
  - 当前脚本目录怎么分层

### 7. 结构总览
示例命名：

- `docs/project-structure-overview.md`

作用：

- 用更面向人的语言，解释整个项目现在有哪些场景、脚本目录、Prefab 入口和工作流

### 8. 玩法规范
示例命名：

- `docs/gameplay-spec.md`

作用：

- 记录“当前项目真正要做成什么玩法”
- 这是最必须按项目实际内容重写的文档之一

### 9. 人工验证清单
示例命名：

- `docs/manual-validation-checklist.md`

作用：

- 让用户把 Unity 内检查结果直接写回文档
- 让智能体后续按“结果：不通过 / 备注”继续修问题

## 四、哪些内容可以复用，哪些必须重写
这是新项目最容易做错的一步。

### 可以复用的模板部分

- 文档体系本身
- 目录结构
- `AGENTS.md` 的章节结构
- 记忆文档的分工方式
- 文档更新触发机制
- 人工验证清单的写法
- 脚本目录分层原则

### 必须按项目实际内容重写的部分

- 项目名称
- 实际玩法规则
- 场景名称
- 模块职责
- 脚本目录名称
- 验证清单里的检查项
- 美术替换工作流
- 技术栈细节
- skill 的触发条件和内容

最重要的一条原则是：

不要把旧项目的内容原样复制过去，只能复制“结构”，不能复制“事实”。

## 五、`AGENTS.md` 应该怎么写
推荐结构如下：

```md
# AGENTS.md

## Workspace Identity
## Startup Protocol
## Operating Rules
## Project-Specific Rules
## Memory Update Triggers
```

### `Startup Protocol` 应该写什么
至少明确：

1. 先读 `AGENTS.md`
2. 再读主记忆文档
3. 按任务类型决定是否补读：
   - 架构文档
   - 规则与历史
   - 玩法规范

### `Project-Specific Rules` 应该写什么
推荐至少包含：

- 中文不能乱码
- 新需求先复述理解
- 未获执行确认前不改文件
- 优先 Scene / Inspector 友好
- 美术替换友好
- 新脚本必须按目录分类放置
- 改动后文档要同步更新

### 推荐直接写进 `AGENTS.md` 的智能体准则
这些是本项目验证过非常有用的：

- 每次新需求先复述理解，再执行
- 用户没说“执行”前不改文件
- 文档中文必须正常显示
- 脚本注释中文必须正常显示
- 新脚本必须放进合理分类目录
- 优先显式引用，不依赖对象名
- 场景对象要尽量可在 Scene 里直接改

## 六、记忆文档体系应该怎么分工
推荐的职责边界如下：

### 主记忆文档
写：

- 导航
- 当前状态
- 长期约束
- 阶段进度
- 当前最重要事实

### 架构文档
写：

- 模块分工
- 总控与子组件的职责边界
- 当前采用的架构原则
- 当前系统的长期边界

### 规则与历史文档
写：

- 已知问题
- 最近修复
- 最近决策
- 长期规范

### 开发手册 / playbook
写：

- 开工固定流程
- 收尾验证流程
- 当前优先开发顺序
- 哪些约束必须一直遵守

### 文件指南
写：

- 关键入口文件
- 当前脚本目录
- 改什么先看哪里

## 七、skill 应该怎么设计
这部分最容易过度设计。

### 什么适合做 skill

- 跨项目可复用的固定流程
- 容易重复的操作步骤
- 需要工具配合的标准流程
- 需要成套参考资料的任务

例如：

- Unity 场景作者化工具使用说明
- 文档修复流程
- Prefab 批量重建流程
- 验证清单读取与追问题流程

### 什么不适合做 skill

- 当前项目独有的一次性事实
- 频繁变化的具体玩法内容
- 本该写在记忆文档里的项目现状
- 本该写在 `AGENTS.md` 的长期执行规则

### 一个实用判断标准

如果某段内容是在回答：

- “这个项目现在是什么状态”

那应该进记忆文档。

如果是在回答：

- “以后反复遇到这类任务时，应该怎么做”

那更适合做 skill。

### 给其他游戏项目的 skill 写法建议
skill 本身写的是“流程”，不是“塔防内容”。

但是 skill 里引用的示例、参考文档、参数说明，必须按实际游戏内容定制。

例如：

- 塔防项目：
  - 关卡路线、建塔规则、供电系统
- 平台跳跃项目：
  - 跳跃手感、关卡检查点、敌人巡逻
- 生存建造项目：
  - 资源采集、建筑配方、昼夜循环

也就是说：

- skill 结构可复用
- skill 内容必须贴项目真实玩法

## 八、文档更新机制怎么定
推荐强制约定：

当以下内容发生变化后，必须更新记忆文档：

- 核心玩法规则
- 场景结构
- UI 层级
- 关键脚本
- 文件结构
- 已知问题
- 验证状态
- 推荐开发顺序

另外，还应该明确：

- 文件结构变化后要刷新索引
- 路径变了要同步改文件指南和结构总览

## 九、新项目初始化时的落地顺序
推荐顺序：

1. 建 `docs/` 与 `docs/ai-memory/`
2. 写 `AGENTS.md`
3. 写主记忆文档
4. 写架构文档
5. 写规则与历史文档
6. 写开发手册
7. 写文件指南
8. 写玩法规范
9. 写人工验证清单
10. 建脚本分类目录
11. 再开始写功能代码

不要反过来：

- 先写一大堆代码
- 最后才补文档

因为那样几乎一定会漏规则、漏背景、漏历史。

## 十、一个可直接复用的新项目初始化清单
下面这份清单可以直接给其他智能体照着做。

### 第一阶段：建骨架

- 创建 `AGENTS.md`
- 创建 `docs/`
- 创建 `docs/ai-memory/`
- 创建主记忆文档
- 创建架构文档
- 创建规则与历史文档
- 创建开发手册
- 创建文件指南
- 创建玩法规范
- 创建人工验证清单

### 第二阶段：写规则

- 写 Startup Protocol
- 写智能体执行规则
- 写文档更新触发条件
- 写中文编码要求
- 写脚本目录分层要求

### 第三阶段：写项目事实

- 写当前玩法目标
- 写当前场景清单
- 写当前入口场景
- 写当前脚本目录
- 写当前技术栈

### 第四阶段：建立验证机制

- 定义人工验证清单格式
- 约定用户把验证结果直接写回文档
- 约定智能体优先读取验证清单继续修问题

### 第五阶段：补 skill

- 只为高复用流程建 skill
- 不要把项目事实塞进 skill
- skill 只写流程、工具和资源
- skill 示例内容按当前项目玩法重写

## 十一、一个简单原则
如果一个新项目希望让多个智能体长期接手，
那就不要只给它“代码仓库”，要同时给它：

- 入口规则
- 记忆结构
- 文档分工
- 验证机制
- 可复用流程

这五样东西一起存在，项目才算真正具备“可持续 AI 协作环境”。
