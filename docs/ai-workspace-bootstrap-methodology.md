# 新项目 AI 工作环境搭建方法论
Updated: 2026-04-23

## 这份文档的定位
这不是“当前塔防项目介绍”，而是一份可复用的方法论文档。  
它的目标是告诉其他智能体：
- 进入一个新的 Unity 项目后
- 应该先建立哪些基础文档与规则
- 如何快速搭出和当前项目同等级的 AI 协作环境

## 一、不要先写代码，先搭协作环境
如果一个项目希望让多个智能体长期接手，第一步不是马上写玩法代码，而是先搭协作环境。

原因很简单：
- 没有统一入口文档，智能体每次都要重新猜项目规则。
- 没有记忆体系，长期项目会不断重复沟通同样的问题。
- 没有验证清单，后期问题会越来越难追。
- 没有文件分层约束，脚本和文档会很快失控。

推荐顺序永远是：
1. 先建文档骨架
2. 再写智能体准则
3. 再定义 skill 与工作流边界
4. 最后再开始正式做功能

## 二、推荐的基础目录结构
新 Unity 项目建议至少先建立：

```text
AGENTS.md
docs/
  ai-memory/
    memory-index.paths.txt
    <project>-memory-main.md
    <project>-memory-architecture.md
    <project>-memory-rules-and-history.md
    <project>-agent-development-playbook.md
    <project>-project-file-guide.md
    tools/
  gameplay-spec.md
  manual-validation-checklist.md
  project-structure-overview.md
  art-replacement-workflow.md
```

如果是 Unity 项目，再预留脚本分层目录：

```text
Assets/Scripts/<ProjectName>/
  Core/
  Map/
  Placement/
  Towers/
  Enemies/
  UI/
Assets/Editor/<ProjectName>/
  Authoring/
  Validation/
```

## 三、必备文档清单
### 1. `AGENTS.md`
作用：
- 作为项目入口说明
- 告诉智能体先读什么、后读什么
- 约束执行方式与文档更新机制

### 2. 主记忆文档
示例：
- `docs/ai-memory/<project>-memory-main.md`

作用：
- 汇总导航、当前状态、长期约束、关键事实、阶段结论

### 3. 架构文档
示例：
- `docs/ai-memory/<project>-memory-architecture.md`

作用：
- 解释模块边界
- 记录长期结构原则

### 4. 规则与历史文档
示例：
- `docs/ai-memory/<project>-memory-rules-and-history.md`

作用：
- 记录项目长期规则
- 记录最近重要交付、已知问题、协作现实

### 5. 开发手册 / playbook
示例：
- `docs/ai-memory/<project>-agent-development-playbook.md`

作用：
- 告诉后续智能体每次开工前要怎么进入项目
- 告诉后续智能体当前优先顺序是什么

### 6. 文件指南
示例：
- `docs/ai-memory/<project>-project-file-guide.md`

作用：
- 快速告诉智能体改什么先看哪里

### 7. 项目结构总览
示例：
- `docs/project-structure-overview.md`

作用：
- 用更面向人的方式，解释当前项目有哪些场景、脚本目录、Prefab 与工作流

### 8. 玩法规范
示例：
- `docs/gameplay-spec.md`

作用：
- 记录当前项目真正要实现的玩法规则
- 这部分必须按项目实际内容重写

### 9. 人工验证清单
示例：
- `docs/manual-validation-checklist.md`

作用：
- 让用户把 Unity 内的检查结果直接写回文档
- 让后续智能体优先读取人工验证结果再继续修问题

## 四、哪些内容可以复用，哪些必须重写
### 可以复用的
- 文档体系本身
- 目录结构
- `AGENTS.md` 的章节结构
- 记忆文档的分工方式
- 文档更新触发机制
- 人工验证清单的写法
- 脚本分层原则

### 必须按项目实际内容重写的
- 项目名称
- 玩法规则
- 场景名称
- 模块职责
- 技术栈细节
- 美术替换工作流
- 验证清单中的具体检查项
- skill 中引用的项目事实

核心原则：
只能复用“结构”，不能原样复制“旧项目事实”。

## 五、推荐直接写进项目规则的智能体准则
下面这些规则，是当前项目长期验证下来最有用的一组：

### 需求沟通
- 每次新需求先复述理解。
- 未得到“执行”前，不修改项目文件。
- 如果用户说的是“大阶段”，只在阶段开始时确认一次；阶段内部可自行分步推进。

### 中文质量
- 文档中的中文不能乱码。
- 脚本注释中的中文不能乱码。

### 目录纪律
- 运行时脚本必须放进合理分层目录。
- 编辑器脚本必须放进 `Authoring` 或 `Validation` 等明确目录。
- 不允许把新脚本散放在根目录。

### 作者工作流
- 优先 Scene 友好、Inspector 友好、显式引用友好。
- 优先让用户能自己在 Scene 里继续编辑地图、UI、Prefab。

### 美术替换友好
- 当前美术默认视为占位资源。
- 避免逻辑依赖具体对象名、占位 Sprite、占位材质和占位颜色。

## 六、skill 应该怎么设计
### 适合做 skill 的
- 跨项目可复用的固定流程
- 容易反复执行的步骤
- 需要工具协作的标准流程
- 需要引用一组固定参考资料的任务

示例：
- 读取记忆文档的标准顺序
- 更新记忆文档的收尾流程
- 人工验收结果读取流程
- 项目文件指南维护流程

### 不适合做 skill 的
- 当前项目独有、会频繁变化的事实
- 当前项目的一次性实现细节
- 本该写进 `AGENTS.md` 的长期规则
- 本该写进记忆文档的当前状态

判断标准：
- 回答“这个项目现在是什么样”时，写进记忆文档
- 回答“以后重复遇到这种任务应该怎么做”时，更适合做 skill

## 七、文档更新机制怎么定
推荐强制约定：
只要以下内容发生实质变化，就更新记忆文档：
- 核心玩法规则
- 场景结构
- UI 层级
- Prefab 结构
- 关键脚本职责
- 已知问题
- 验证状态
- 推荐开发顺序

另外要明确：
- 文件结构变了，要刷新索引
- 路径变了，要同步改文件指南和结构总览

## 八、新项目初始化时的落地顺序
1. 建 `docs/` 与 `docs/ai-memory/`
2. 建 `AGENTS.md`
3. 写主记忆文档
4. 写架构文档
5. 写规则与历史文档
6. 写开发手册
7. 写文件指南
8. 写玩法规范
9. 写人工验证清单
10. 建脚本分层目录
11. 再开始正式做功能代码

## 九、一个可直接复用的初始化清单
### 第一阶段：建骨架
- 创建 `AGENTS.md`
- 创建 `docs/`
- 创建 `docs/ai-memory/`
- 创建主记忆文档、架构文档、规则与历史文档
- 创建开发手册、文件指南、玩法规范、人工验证清单

### 第二阶段：写规则
- 写 Startup Protocol
- 写智能体执行规则
- 写文档更新触发条件
- 写中文质量规则
- 写脚本分层规则

### 第三阶段：写项目事实
- 写当前玩法目标
- 写当前场景清单
- 写关键文件入口
- 写当前技术栈与目录结构

### 第四阶段：补 skill
- 只为高复用流程建 skill
- 不要把项目事实塞进 skill
- skill 只写流程、工具和资源组织方式

## 十、一个简单原则
如果一个新项目希望让多个智能体长期接手，
那就不要只给它“代码仓库”，而要同时给它：
- 入口规则
- 记忆体系
- 文档分工
- 验证机制
- 可复用流程

这五样东西一起存在，项目才真正具备“可持续 AI 协作环境”。
